# «Выбор и настройка мониторинга в системе»

Документ опирается на условие, [схему C4](../jewerly_c4_model.drawio) и допущения из [README](../README.md) (Д1–Д8).

## Анализ системы

### Что есть сейчас

- Из инструментов в условии упомянута только Яндекс Метрика на сайте магазина. Она показывает посетителей сайта, а после запуска оформления заказов через API этих данных уже недостаточно.
- Алертов нет (Д5), поэтому о проблемах команда узнаёт от клиентов: они жалуются менеджерам по продажам.

### Выводы для мониторинга

1. Измерять нужно на трёх уровнях: внешний трафик API, сервисы (три API) и ресурсы (БД, инстансы, RabbitMQ, хранилище).
2. Одних ресурсов (CPU, память) недостаточно. Заказ может зависнуть при нормальной загрузке серверов, например в очереди или в ожидании передачи. Нужны метрики очереди и «возраста» незавершённых операций.
3. MES API выполняет разнородную работу в одном инстансе (Д3), поэтому метрики должны различать виды запросов с помощью ярлыков.
4. Каждое приложение и каждая БД работают в одном экземпляре, и недоступность любого из них останавливает свою часть потока заказа. Нужны проверка доступности и алерт.
5. Внешний канал API нужно видеть в разрезе клиентов: Яндекс Метрика его не покрывает.

## Мотивация

Сейчас компания узнаёт о сбоях с заказами от клиентов, когда контракт уже под угрозой. Мониторинг переносит момент обнаружения раньше, показывает, что чинить первым, и позволяет проверить, что исправление сработало.

### Что происходит сейчас

- **О проблемах компания узнаёт от клиентов.** Клиенты жалуются менеджерам по продажам, что над заказом работают месяцами вместо трёх недель. Представители API-клиентов ежедневно сообщают, что не получили заказы. Операторы жалуются на медленную первую страницу MES. Сигнала от самой системы до этих жалоб нет (Д5).
- **Последствия уже дорогие.** Через месяц после открытия API компания потеряла несколько крупных контрактов, недовольство B2C-клиентов растёт.
- **Картины по системе нет.** Единственный упомянутый инструмент — Яндекс Метрика на сайте магазина. После запуска оформления заказов через API её данных недостаточно, а работу API, очереди, баз и хранилища она не показывает.
- **Улучшения делаются вслепую.** Для дашборда ввели фильтр по статусам и пагинацию, но это не помогло. Без измерений непонятно, где узкое место: запрос к базе, загрузка инстанса или конкуренция с расчётом цены в том же процессе (Д3).
- **Нагрузка растёт, а запас неизвестен.** Каждый месяц приходит на 100 заказов больше, а приложения и базы работают в одном экземпляре. Производство выдержит двукратный рост, но выдержит ли его ИТ-контур, сейчас измерить нечем.

### Что даст мониторинг компании

| Что даёт                           | Как это выглядит на практике                                                                                                                                                                         |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Узнавать о проблеме раньше клиента | Алерты на рост очереди и сообщения без обработки, на заказы, которые слишком долго ждут передачи или расчёта, на рост ошибок API. Цепочку «клиент → менеджер → команда» заменяет «система → команда» |
| Видеть каналы по отдельности       | Магазин и внешний API в разрезе клиентов. Для крупного клиента можно посмотреть его запросы, ошибки и задержки и ответить на жалобу фактами                                                          |
| Решать, что чинить первым          | Данные показывают, где узкое место (перегруженный MES API, очередь, база), вместо догадок по жалобам                                                                                                 |
| Доказывать эффект изменений        | Сравнение «до и после» по задержкам, ошибкам и очередям. Бизнес видит отдачу от вложений в улучшения                                                                                                 |
| Планировать мощности               | По росту загрузки CPU, памяти, соединений и размера баз видно, когда система упрётся в предел инстанса, и можно подготовиться заранее                                                                |

Мониторинг сам заказы не ускоряет: он показывает, где проблема, и сокращает время реакции. Исправления остаются отдельной работой.

### Почему это стоит ресурсов команды

- **Отсутствие мониторинга уже обходится дорого.** Потеряны крупные контракты, а жалобы клиентов приходят к менеджерам по продажам, а не к команде.
- **Вложение небольшое.** Предлагаемый стек (Prometheus и Grafana) не требует лицензий, основная стоимость — время команды на подключение. Он ставится рядом с приложениями и не меняет бизнес-логику.
- **Внедрять можно постепенно.** По окружениям (dev → release → prod) и по частям, начиная с самых проблемных мест: MES API и очереди.
- **Без измерений остальные вложения теряют смысл.** Эффект любого улучшения нечем подтвердить, как в истории с фильтром и пагинацией.

### Как поймём, что мониторинг окупился

Базовых значений сейчас нет, они появятся в первые недели работы мониторинга. Затем следим за показателями:

- время от возникновения проблемы до её обнаружения командой (сейчас — до жалобы клиента);
- доля проблем, которые команда заметила раньше клиентов;
- число жалоб клиентов и API-пользователей на несданные или просроченные заказы;
- число заказов, которые находятся в работе дольше обещанных трёх недель, и как быстро мы это замечаем.

## Выбор подхода к мониторингу

Один подход на всю систему не подойдёт: у сервисов, баз и очереди разные вопросы к мониторингу.

### Три подхода

| Подход                 | Что измеряет                                                                            | Для чего подходит                                                  |
| ---------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| RED                    | Rate — число запросов, Errors — доля ошибок, Duration — время ответа                    | Сервисы, которые обрабатывают запросы                              |
| USE                    | Utilization — занятость ресурса, Saturation — очередь ожидающей работы, Errors — ошибки | Ресурсы: серверы, базы, очереди, хранилища                         |
| Четыре золотых сигнала | Latency — задержка, Traffic — трафик, Errors — ошибки, Saturation — насыщенность        | Сервисы, у которых важен предел ёмкости: это RED плюс насыщенность |

### Выбор по частям системы

| Часть системы                                    | Подход                                    | Почему                                                                                                                                                                                                                                                              |
| ------------------------------------------------ | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Shop API                                         | RED                                       | Обычный сервис «запрос — ответ» (покупатели, загрузка файлов). Главные вопросы: сколько запросов, сколько ошибок, как быстро отвечает. Загрузку сервера видно отдельно по USE инстанса                                                                              |
| CRM API                                          | RED                                       | То же для HTTP-запросов продавцов. Фоновую работу (опрос Shop DB по Д1, отправку и приём сообщений) RED не покрывает, её видно по метрикам RabbitMQ и по метрикам процесса заказа (см. раздел «Метрики»)                                                            |
| MES API                                          | Четыре золотых сигнала                    | В одном экземпляре сразу три вида работы: расчёт цены до 30 минут, дашборд операторов и запросы API-клиентов (Д3, Д6, Д8). Один вид может забрать ресурсы у остальных, поэтому нужна насыщенность, а задержку и трафик нужно делить по видам запросов и по клиентам |
| Внешний канал API (сторонние продавцы → MES API) | Четыре золотых сигнала, в составе MES API | Это те же запросы в MES API, отдельный подход не нужен. Нужен разрез по клиентам (`client`): трафик, ошибки и задержка каждого клиента (Д6). Яндекс Метрика этот канал не покрывает                                                                                 |
| Shop DB, MES db                                  | USE                                       | Это ресурсы, а не сервисы. Один инстанс и на запись, и на чтение, поэтому важны занятость (память, подключения, размер) и насыщенность (ожидающие подключения). Для MES db сюда входит и нагрузка от дашборда (Д8)                                                  |
| Инстансы Shop API, CRM API и MES API (EC2)       | USE                                       | По одному инстансу на приложение: CPU и память сервера показывают, что приложение подошло к пределу. Дополняет RED и золотые сигналы на уровне сервера                                                                                                              |
| RabbitMQ                                         | USE                                       | Единственный канал между CRM и MES. Вопрос не «сколько запросов», а «копится ли очередь»: занятость, насыщенность (сообщения ждут, возраст самого старого) и ошибки (сообщения в dead-letter-очереди). Без этого потерю и зависание сообщений не заметить (Д5)      |
| Хранилище 3D-файлов                              | USE в сокращённом виде                    | У хранилища объектов нет очереди ожидающей работы, поэтому насыщенность неприменима. Смотрим занятость (рост размера) и ошибки обращений                                                                                                                            |

### Почему именно так

- Только RED не опишет базу и очередь: у них важны занятость и накопление, а не запросы.
- Только USE не покажет, как быстро система отвечает клиентам: сервер может быть не загружен, а ответы медленными.
- Золотые сигналы для всех сервисов удвоили бы работу без пользы: для Shop API и CRM API насыщенность уже видна по USE их серверов.
- В итоге каждый сервис виден двумя слоями: сверху RED (для MES API золотые сигналы), снизу USE сервера и базы.

Метрики из списка задания распределены по этим подходам в следующем разделе. Там же добавлены свои метрики для того, что список и подходы не покрывают.

## Метрики

### Как формулируем метрики

- **Одна метрика на три приложения.** Метрики Shop API, CRM API и MES API из списка отличаются только сервисом. Вместо трёх отдельных заводим одну метрику с ярлыком `service` (`shop`, `crm`, `mes`). Так проще строить дашборды и добавлять сервисы.
- **Классы ответов вместо конкретных кодов.** HTTP 200 и 500 из списка заменяем ярлыком `status_class` (`2xx`, `4xx`, `5xx`). В списке нет 4xx, а для внешних клиентов это важно.
- **Процентили вместо среднего** для времени ответа: среднее скрывает медленные ответы.
- **Ярлыки с ограниченным числом значений.** Число значений ярлыка должно быть ограниченным и известным заранее, иначе число рядов метрик разрастается и хранилище замедляется. Поэтому `orderId` в ярлыки не идёт: каждый новый заказ даёт новое значение, и рядов становится всё больше. Сколько покупателей у магазина, мы пока не знаем: число конечно, но границы не видно. Точно известно только, что каждый месяц приходит на 100 заказов больше, чем в предыдущий, поэтому число значений, скорее всего, будет расти. Значением `user` служит внутренний идентификатор покупателя (псевдоним), а не имя или почта. Ярлык `user` вводим с контролем числа рядов и пересматриваем по данным первых недель. Если рядов окажется слишком много, для покупателей перейдём на учёт самых активных (топ-N). Для `endpoint` берём шаблон маршрута (например, `/orders/{id}`), а не конкретный URL.

## План действий

Драфт технического задания. Задачи высокоуровневые, детали уточняем при проработке. Не входят в это ТЗ: правила повторной обработки сообщений в приложениях, трейсинг и централизованные логи.

### Стек

Prometheus собирает и хранит метрики, Alertmanager рассылает алерты, Grafana строит дашборды. Причины выбора:

- открытый код, без лицензий;
- для каждого объекта есть готовый способ получить метрики: Micrometer для Spring Boot, prometheus-net для C#, встроенный плагин RabbitMQ, postgres_exporter для PostgreSQL, node_exporter для серверов;
- сбор «по запросу» (pull) сам показывает, что цель недоступна (метрика `up`), это закрывает метрику доступности;
- ярлыки и язык запросов PromQL подходят для нужных разрезов (`service`, `endpoint`, `client`);
- стек достаточно прост, чтобы им занимался один DevOps-инженер.

Метрики управляемых баз Yandex Cloud, которых нет у postgres_exporter (CPU, память и диск хоста), берём из Yandex Monitoring и показываем в той же Grafana.

## Показатели насыщенности

Насыщенность показывает, насколько компонент близок к пределу. Для нас это особенно важно: приложения и базы работают в одном экземпляре, запаса нет, и после предела страдает весь поток заказа. Показатели выбраны так, чтобы дать время среагировать до отказа и покрыть узкие места, из-за которых идут жалобы: расчёт цены и дашборд в MES API (Д3, Д8), очередь между CRM и MES, базы и пиковая нагрузка магазина.

Пороги стартовые. Мы уточним их по базовым значениям первых недель и по нагрузочной проверке в release. Где абсолютных данных нет, порог задан относительно базового значения или проверенной ёмкости:

- **Базовое значение** — значение метрики в обычные дни первых недель работы мониторинга.
- **Проверенная ёмкость** — нагрузка, которую один экземпляр выдерживает без заметной деградации (RPS и сессии для Shop API, число расчётов в работе для MES API). Определяется нагрузочной проверкой в release.

| Память трёх API                                                   | ≥ 80%                                               | ≥ 90%                                                                        | Нехватка памяти останавливает приложение, а другого экземпляра нет. В MES расход растёт на сложных 3D-моделях                                                                             |
| Число подключений к БД                                            | ≥ 70% лимита                                        | ≥ 85% лимита                                                                 | Исчерпанный лимит останавливает работу с базой. Нужен запас на всплески: дашборд ходит в MES db на каждый запрос (Д8), расчёты и записи идут параллельно                                  |
| Память БД (занятая, без кэша)                                     | ≥ 85%                                               | ≥ 95%                                                                        | Один инстанс и на чтение, и на запись: нехватка замедляет все операции. Кэш файловой системы не считаем, он занимает память штатно                                                        |
| Размер БД (заполнение диска)                                      | ≥ 70% или заполнится за 30 суток                    | ≥ 85% или заполнится за 7 суток                                              | Полный диск останавливает базу. Заказов каждый месяц больше, рост ускоряется, поэтому прогноз надёжнее порога в процентах. Срок нужен, чтобы расширить диск заранее                       |
| Нагрузка Shop API (RPS и сессии) относительно проверенной ёмкости | ≥ 70%                                               | ≥ 85%                                                                        | Один экземпляр должен выдержать и пиковые дни, например Чёрную пятницу. Порог считаем от ёмкости, найденной нагрузочной проверкой, чтобы успеть подготовиться до пика                     |
| Расчёты цены в работе относительно проверенной ёмкости MES API    | ≥ 70%                                               | ≥ 90%                                                                        | Прямой показатель насыщенности MES API (Д3): пока расчёты не вытесняют дашборд, ёмкость есть                                                                                              |
| Время ответа (p95) трёх API                                       | ≥ 1,5× базового в течение 10 минут                  | ≥ 2× базового в течение 10 минут                                             | Итоговый сигнал: перегрузку пользователь чувствует через задержку. Порог относительный, потому что базовых значений пока нет                                                              |
| Скорость роста размера хранилища 3D-файлов                        | Недельный рост ≥ 2× среднего за предыдущие 4 недели | Не задаём                                                                    | У хранилища объектов нет предела, поэтому смотрим на резкий рост: это лишние расходы или необычная загрузка файлов                                                                        |

### Что происходит при превышении

| Уровень        | Как оповещаем                                                                                                                       | Что делаем                                                                                                                                                | Кто                                       |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Предупреждение | Сообщение в канал команды, автоматически заводится тикет                                                                            | Разобрать в рабочее время, оценить запас и решить, что менять: мощность, настройки, набор метрик                                                          | DevOps, разработчики затронутого сервиса  |
| Критично       | Немедленно дежурному в мессенджер и по почте, повтор каждые 15 минут до подтверждения, через 30 минут без реакции эскалация тимлиду | Действовать по runbook, записать инцидент в журнал, при влиянии на клиентов сообщить продакт-менеджеру, чтобы менеджеры по продажам предупредили клиентов | Дежурный DevOps, тимлид, продакт-менеджер |

Порядок дежурства определяет тимлид, интервалы повтора и эскалации стартовые.

**Автоматических действий на старте нет.** У приложений по одному экземпляру и нет масштабирования, поэтому реакция ручная, по runbook. Если масштабирование появится, подключим его к порогам «Предупреждение» по нагрузке. Для критичных алертов в prod можно добавить автодозвон дежурному, если будет организовано круглосуточное дежурство.

**Первые действия по показателям:**

| Показатель              | Что делаем                                                                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Очередь на расчёт цены  | Проверить, что потребитель MES работает и не завис на тяжёлом расчёте, при зависании перезапустить. Предупредить продавцов и продакт-менеджера о задержке цен                              |
| CPU и память приложений | Определить источник по ярлыкам (`endpoint`, `caller_type`, `client`): расчёт, дашборд или внешний API. Увеличить мощность инстанса. Если нагрузку создаёт один клиент API, связаться с ним |
| Подключения и память БД | Найти приложение, которое занимает подключения. Увеличить лимит или класс хоста БД в управляемом сервисе                                                                                   |
| Размер БД               | Расширить диск в управляемом сервисе и запланировать очистку данных                                                                                                                        |
| Нагрузка Shop API       | До пикового дня заранее увеличить мощность инстанса по итогам нагрузочной проверки                                                                                                         |
| Время ответа            | Посмотреть, какой из показателей выше нарушен, и действовать по нему                                                                                                                       |
