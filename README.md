# Проектная работа 6 спринта: кейс «Александрит»

Архитектурные решения по кейсу компании «Александрит» (производство ювелирных украшений на заказ).

- Исходная C4-диаграмма контейнеров: [jewerly_c4_model.drawio](jewerly_c4_model.drawio)

## Допущения, на которых построены решения

Условие и схема описывают систему не полностью. Поэтому был зафиксирован один вариант того, как система работает, и все задания опираются на него.

Ниже только ключевые допущения и причины, по которым они приняты. Каждое выбрано так, чтобы:

1. не противоречить условию и схеме;
2. быть самым простым объяснением при отсутствии другой информации;
3. согласовываться с симптомами из условия (потерянные заказы, тормозящий дашборд, растущие задержки).

| ID     | Что принято                                                                                                                                                                                                              | Почему так                                                                                                                                                                                                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Д1** | Заказ из магазина попадает в RabbitMQ через CRM API, который периодически опрашивает Shop DB на статус `SUBMITTED`                                                                                                       | На схеме Shop API не связан с RabbitMQ, а CRM API связан и с Shop DB, и с очередью. Другого пути от магазина к MES нет. Опрос выбран как самый простой механизм: никаких событий на стороне Shop DB на схеме не показано                                                                                             |
| **Д2** | MES узнаёт о заказе и о файле только из сообщения `order.submitted` с ключом файла в S3                                                                                                                                  | От S3 к MES и к очереди стрелок нет, значит уведомлений о загрузке файла нет. К тому же MES нужен идентификатор заказа, а его в S3 нет                                                                                                                                                                               |
| **Д3** | Цена считается внутри MES API, в том же инстансе, что дашборд оператора и запросы API-клиентов. Отдельных воркеров нет                                                                                                   | MES API на схеме один, в его описании: назначает заказы, показывает список, считает цену. Отдельного сервиса расчёта нет. По условию у каждого приложения один инстанс. Расчёт по условию идёт «на стороне MES». Это согласуется с тем, что жалобы на дашборд и просроченные заказы растут вместе с нагрузкой на API |
| **Д4** | Сквозного идентификатора между системами нет, заказ связывается только по `orderId`. Названия сообщений (`order.submitted` и другие) условные                                                                            | В условии нет ни трейсинга, ни логирования, и команда не может понять, где находится заказ. Названия придуманы нами, чтобы описывать точки передачи заказа                                                                                                                                                           |
| **Д5** | В интеграции через RabbitMQ нет outbox, идемпотентности потребителей, DLQ и алертов. Потерянное или зависшее сообщение никто не замечает                                                                                 | Интеграцию написала команда «Александрита», о гарантиях доставки в условии ничего нет. Заказы «теряются» и «висят месяцами», и о проблеме узнают от клиентов, то есть контроля нет. Мониторинга в системе тоже нет. Допущение выбрано как наиболее согласующееся с симптомами                                        |
| **Д6** | API-сценарий асинхронный: MES API сразу отвечает идентификатором запроса, результат клиент получает опросом. Push и webhook нет. После расчёта MES публикует сообщение, CRM создаёт заказ со статусом `PRICE_CALCULATED` | Расчёт занимает до 30 минут, держать HTTP-соединение так долго нецелесообразно. В условии сказано, что заказ в CRM создаётся «через получение сообщения из очереди от MES». У API user на схеме одна стрелка, в MES API, обратных каналов нет                                                                        |
| **Д7** | Статусы хранятся в двух местах: в Shop DB и в MES db. Синхронизируются только сообщениями, единого источника истины нет. Магазин показывает покупателю статус из Shop DB                                                 | Shop DB описана как «основная информация о заказах», MES db как «статусы с точки зрения MES». Других связей между системами кроме очереди на схеме нет                                                                                                                                                               |
| **Д8** | При каждом запросе списка заказов (открытие дашборда MES, смена фильтра или страницы) MES API читает его из MES db. Кеша нет                                                                                             | В условии кеширование не упоминается. Команда уже пробовала фильтр по статусам и пагинацию, значит запрос идёт в БД. Между MES API и MES db на схеме нет промежуточных компонентов                                                                                                                                   |
