# «Архитектурное решение по логированию»

Документ опирается на условие, [схему C4](../jewerly_c4_model.drawio) и допущения из [README](../README.md) (Д1–Д8).

## Анализ системы

Сейчас ошибки и нестандартные ситуации разбираются со слов клиента, а разработчикам и поддержке нужно много времени, чтобы понять, что произошло внутри сервисов. Логи отвечают на вопрос «что именно случилось и почему». Метрики из [Task2](../Task2/Task2.md) показывают, что и сколько, трейсы из [Task3](../Task3/Task3.md) показывают, где заказ. Логи и их хранение дорогие, поэтому собираем минимум: только то, чего нет в метриках и трейсах.

### Логи уровня INFO

INFO — это события, по которым видно, что происходило с заказом, без чтения кода. Записей на заказ немного, поэтому объём логов растёт вместе с числом заказов, а не с числом запросов. Идентификатор пользователя во всех записях внутренний (как `user` в метриках Task2), имени и почты в логах нет.

| --------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

В prod минимальный уровень INFO.

Для записей ERROR и WARN, по которым работают правила из раздела «От сбора к анализу», фиксируем постоянные имена `event.action` (например, `file.not_found`, `status.transition.invalid`). Справочник имён ведёт команда вместе с форматом записи.

**Записи о сбоях по заказу.** Поддержка должна видеть, что случилось с заказом, иначе за каждым сбоем ей придётся идти к разработчикам. Поэтому, если сбой или отклонение затрагивает конкретный заказ, приложение пишет две записи. Техническая (ERROR или WARN со стеком и подробностями) уходит в индекс системы и доступна разработчикам. Запись о заказе (уровень WARN, `event.action` из справочника, `event.outcome=failure`, `order.id`, `error.type`, короткий постоянный текст, без стека и данных запроса) уходит в `logs-orders` и доступна поддержке. Например, для `file.not_found` поддержка видит «файл заказа не найден», а разработчик ещё и стек с контекстом.

### Формат записи

Каждая запись — одна JSON-строка. Имена полей берём из Elastic Common Schema там, где такие поля есть, поля заказа свои, как в трейсинге.

| Поле                                                        | Пример                                                     | Зачем                                                                                                           |
| ----------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `@timestamp`                                                | `2026-09-26T10:15:30.123Z`                                 | Время события в UTC. Часы инстансов синхронизированы                                                            |
| `log.level`                                                 | `INFO`                                                     | Уровень                                                                                                         |
| `service.name`, `service.version`, `deployment.environment` | `mes-api`, `1.14.2`, `prod`                                | Какой сервис, какой версии и в каком окружении. По версии видно, после какого релиза начались проблемы          |
| `event.action`, `event.outcome`                             | `order.status.changed`, `success`                          | Постоянное имя события и результат. По ним ищем и считаем                                                       |
| `message`                                                   | «Status changed»                                           | Короткий постоянный текст без данных, а данные лежат в полях                                                    |
| `order.id`                                                  | `1042`                                                     | Ключ поиска по заказу, когда он известен                                                                        |
| `trace.id`, `span.id`                                       | Из контекста трейса                                        | Переход между логом и трейсом ([Task3](../Task3/Task3.md)). Trace id есть в каждой записи                       |
| `user.id`, `user.role`                                      | Внутренний идентификатор, `customer`, `seller`, `operator` | Кто действовал. Только там, где это нужно для события                                                           |
| `api.client`                                                | Идентификатор клиента API                                  | Связь событий с клиентом (Д6)                                                                                   |
| `error.type`, `error.stack_trace`                           | Тип и стек                                                 | Для уровня ERROR                                                                                                |
| `stream`                                                    | `order` или `technical`                                    | Куда идёт запись: `order` — в индекс событий заказа, `technical` — в индекс системы. Значение ставит приложение |

Правила:
- запись одной строкой, стек ошибки внутри поля: многострочные записи ломают сбор и поиск;
- данные от внешних клиентов перед записью очищаем от переводов строк и управляющих символов, иначе клиент сможет подделать записи в логе;
- набор полей ограничен утверждённым списком. Новое поле проходит проверку, чтобы в лог не попали лишние данные.

### Чего в логах быть не должно

Список из [Task3](../Task3/Task3.md) переносим полностью и добавляем особенности логов:
- персональные данные покупателей: имя, телефон, почта, адрес доставки. Покупатель допустим только как внутренний идентификатор;
- тела запросов, ответов и сообщений, содержимое 3D-файлов;
- токены, пароли, заголовки `Authorization`, cookie;
- значения параметров SQL-запросов, цены и условия для API-клиентов;
- тексты исключений с данными пользователей: их очищаем до записи, потому что ошибки часто содержат значения, которые не должны попасть в лог;
- успешные запросы приложений целиком (access-лог): нагрузка видна по метрикам, путь заказа по трейсам. Исключение — журнал доступа прокси перед Jaeger и Kibana, он нужен для аудита.

Как это обеспечиваем технически, описано в разделе «Предлагаемое решение».

### Чем логи отличаются от метрик и трейсов

| Инструмент                           | На какой вопрос отвечает                     | Пример                                                            |
| ------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------- |
| Метрики ([Task2](../Task2/Task2.md)) | Сколько и как быстро, в целом по системе     | 12 заказов дольше часа в `SUBMITTED`, доля ошибок MES API выросла |
| Трейсы ([Task3](../Task3/Task3.md))  | Где заказ и сколько времени занял каждый шаг | Заказ 1042: сообщение опубликовано, в MES не получено             |
| Логи                                 | Что именно произошло и почему                | MES не нашёл файл заказа 1042 в хранилище: причина и стек ошибки  |

Метрика сигнализирует о проблеме, трейс показывает место, лог объясняет причину.

В лог не пишем то, что уже есть в другом месте:
- длительность шагов и запросов (метрики и трейсы);
- вход и выход методов (путь запроса виден в трейсе);
- публикацию и получение каждого сообщения при успехе (путь сообщения виден в трейсе), в логе остаются только сбои и повторы;
- записи «ничего не найдено» при опросе Shop DB.

Смена статуса заказа есть и в трейсе, и в логе. Это осознанное пересечение: в трейс покупатель и сотрудники не попадают, а без них журнал заказа неполон.

## Мотивация

Сейчас на вопрос «что произошло с заказом и почему» команда отвечает со слов клиента. Логирование даёт ответ по данным самих сервисов: что случилось, когда и при каких условиях.

### Что происходит сейчас

- **Разбор идёт со слов клиента.** Клиенты рассказывают, как что-то пошло не так, а разработчики и поддержка пытаются понять, что случилось на стороне сервиса. По условию на это уходит очень много времени.
- **Данные о заказе разбросаны.** Заказ проходит через три приложения, очередь и две базы (Д7). Общего идентификатора между системами, кроме `orderId`, нет (Д4), поэтому собрать картину по одному заказу можно только вручную.
- **Ошибки не замечаются сами.** Алертов нет (Д5), о проблеме команда узнаёт от клиентов: API-клиенты ежедневно сообщают, что не получили заказы, клиенты магазина жалуются менеджерам по продажам.
- **Последствия уже дорогие.** Через месяц после открытия API компания потеряла несколько крупных контрактов, недовольство B2C-клиентов растёт. Заказов с каждым месяцем больше, значит, больше обращений и ручного разбора.

### Что даст логирование компании

| Что даёт                                     | Как это выглядит на практике                                                                                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Причина ошибки без расспросов клиента        | По `order.id` поддержка видит, какой сбой произошёл с заказом, а разработчик по trace id ещё и текст ошибки со стеком. Не нужно выяснять у клиента, что он делал     |
| Меньше нагрузки на поддержку и разработчиков | Поддержка сама находит события заказа. Разработчики подключаются, когда причина уже видна, и тратят время на исправление, а не на поиск                              |
| История заказа с указанием, кто действовал   | Смена статуса записывается с ролью и внутренним идентификатором: видно, кто подтвердил заказ, кто взял его в работу. Это ответ на спорные случаи и пример из задания |
| Связь проблемы с релизом                     | В каждой записи есть версия сервиса, видно, что ошибки начались после конкретного релиза                                                                             |
| Раннее обнаружение ошибок                    | Алерты по логам поднимают всплеск ошибок раньше жалоб клиентов (раздел «От сбора к анализу»)                                                                         |
| Основа для поиска аномалий                   | Из логов можно понять, кто именно создаёт необычную нагрузку                                                                                                         |

Логирование само заказы не ускоряет и потери сообщений не устраняет. Оно сокращает время разбора и число расспросов клиента.

### Почему это стоит ресурсов команды

- **Ручной разбор уже обходится дорого.** Каждое обращение требует расспросов клиента и поиска по трём приложениям, а обращений становится больше вместе с числом заказов.
- **Вложение умеренное.** Elasticsearch уже нужен для трейсов ([Task3](../Task3/Task3.md)), для логов добавляются Filebeat, Kibana и диск. Основная работа команды — единый формат записей в трёх приложениях.
- **Логи и их хранение дорогие, поэтому проектируем экономно.** Семь событий уровня INFO вместо записи каждого запроса, нет access-логов приложений, шум и повторяющиеся записи не пишем, сроки хранения разные, размер оцениваем формулой. Стоимость хранения вынесена в отдельную метрику решения.
- **Внедрять можно по частям.** Сначала участок, где теряются заказы, затем остальное. Польза появляется уже после первого этапа.

### Метрики решения

Базовых значений сейчас нет, поэтому числа не задаём. Значения «до» берём из журнала инцидентов, который команда начинает вести по плану [Task2](../Task2/Task2.md) (задача 17), до запуска логирования в prod. Значения «после» сравниваем через первые недели работы.

| Метрика                                        | Тип                    | Как считаем                                                                                                                      | Откуда данные                                           | Как влияет логирование                                                                                                                                                             |
| ---------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Время до установленной причины                 | Техническая            | Медиана времени от сигнала (жалоба или алерт) до установленной причины проблемы: текст ошибки, условия, при которых она возникла | Журнал инцидентов: отметки «сигнал» и «причина найдена» | Главный эффект: причина видна в записи, а не выясняется у клиента. Первые две метрики показывают, работает ли само логирование. Третья и четвёртая показывают, что оно даёт бизнесу, но зависят и от трейсинга ([Task3](../Task3/Task3.md)), и от исправлений, которые помогает найти разбор, поэтому оцениваем их вместе. Последняя не измеряет пользу, а следит за ценой.

### Порядок внедрения логирования и трейсинга

Команда не сможет внедрить логирование и трейсинг сразу во всех системах, поэтому порядок выбран по трём соображениям:
- **Где теряются заказы.** Условие говорит о теряющихся сообщениях и о жалобах API-клиентов, а это участок CRM API → RabbitMQ → MES API (Д1, Д5, Д6). Здесь нужно и место (трейсинг), и причина (логи).
- **Кто в команде свободен.** У MES API один C#-разработчик, это узкое место. Java-разработчиков двое, и у них есть запас. Поэтому изменения в MES API делаем одним проходом: логи и трейсы вместе, чтобы не трогать один и тот же код дважды.
- **Что от чего зависит.** Trace id попадает в запись лога из контекста трейса, поэтому там, где ставим оба инструмента, трейсинг идёт первым или одновременно. Инфраструктура (Elasticsearch, Kibana, Filebeat, Collector) ставится один раз и общая.

## Предлагаемое решение

Схема решения: [jewerly_c4_logging.drawio](jewerly_c4_logging.drawio). Новые компоненты и связи сбора логов выделены красным, компоненты анализа логов и оповещений (сторож, Prometheus и Alertmanager из Task2) — зелёным, системы, из которых собираем логи, — фиолетовой рамкой (сплошная для обязательного сбора, пунктирная для частичного).

Компоненты трейсинга (Collector, Jaeger, узел трейсов Elasticsearch) на этой схеме не показаны, они на схеме [Task3](../Task3/jewerly_c4_tracing.drawio). Общий с трейсами кластер Elasticsearch показан здесь узлом логов.

### Сбор и обработка

1. **Приложение пишет в файл.** Записи в формате JSON уходят в локальный файл через асинхронный вывод, с ротацией по размеру и возрасту и ограничением общего объёма на диске. Приложение не зависит от доступности Elasticsearch и не тормозит из-за него. Лимит на диск обязателен: инстанс единственный, и переполнение диска логами остановит приложение.
2. **Filebeat читает файл.** Он запоминает позицию чтения и при недоступности Elasticsearch повторяет отправку. Условие: ротация не должна удалять файл раньше, чем Filebeat его прочитает, поэтому срок хранения ротированных файлов на инстансе рассчитываем с запасом на время недоступности хранилища.
3. **Обработка на источнике.** Filebeat оставляет только утверждённые поля, добавляет окружение и направляет записи в индекс по полю `stream` и системе: записи заказа в `logs-orders`, остальные в индекс своей системы.
4. **Обработка в Elasticsearch.** Конвейер маскирует значения, похожие на почту, телефон и токен, и проверяет обязательные поля. Это последний рубеж: основная защита в том, что чувствительных данных в записи нет.

**Logstash не используем.** Он нужен там, где логи нужно разбирать, обогащать данными из других систем, отправлять в несколько мест или буферизовать надёжнее файлов. У нас записи сразу в JSON, источников около пяти, обогащения нет, а буфером служат файлы на инстансах. Logstash был бы ещё одной Java-программой, которую единственный DevOps-инженер эксплуатирует и обновляет. Если условия изменятся (источников станет много, появятся неструктурированные логи, нужно обогащение, отправка в несколько мест или более надёжный буфер), Logstash встанет между Filebeat и Elasticsearch без изменений в приложениях.

### Хранение

**Индексы.** Технические логи хранятся отдельным индексом на систему и окружение, события заказа собраны в один сквозной индекс.

Срок — это время до удаления индекса политикой жизненного цикла (ILM). Сроки стартовые, пересматриваем по фактическому объёму.

Почему отдельные индексы, а не один общий:
- у событий заказа и технических записей разные сроки хранения, а срок задаётся на весь индекс;
- права выдаём на индекс: поддержка читает события заказа и записи о сбоях по заказу, но не видит технические записи со стеками ошибок;
- объём по системам можно считать отдельно, это нужно для метрики «объём логов на 100 заказов»;
- события заказа ищутся по `order.id` через все системы, для этого удобен один индекс.

Ожидаем небольшие индексы, поэтому стартуем с одного шарда на индекс и ротации по размеру и возрасту, число шардов пересматриваем по фактическому объёму. Реплик нет (см. раздел «Размещение»).

**Размер.** Числа объёма мы не знаем и измеряем в dev и release до выката в prod. Оцениваем формулой:

`объём индекса в месяц = записей в месяц × средний размер записи × коэффициент индексации`

`место под индекс = объём в месяц × срок хранения в месяцах`

- **События заказа:** записей в месяц = число заказов × записей на заказ. Записей на заказ порядка десятка-двух: десять статусов из условия, часть из них записывается в двух системах (Д7), плюс загрузка файла и передача заказа в MES. Число заказов растёт каждый месяц на 100 больше, чем в предыдущий, поэтому объём индекса заказов растёт линейно и нужен запас.
- **Технические записи:** зависят от числа ошибок и повторов, а не от числа заказов. Оцениваем в release и ограничиваем предельным размером индекса при ротации, чтобы шум не съел диск.
- **Коэффициент индексации** (насколько индекс больше исходных данных) измеряем на тестовых данных.

Ограничители стоимости: ротация по размеру, удаление по сроку, алерты на заполнение диска (пороги как для баз в [Task2](../Task2/Task2.md)), метрика «объём логов на 100 заказов».

### Политика безопасности

**Чувствительные данные.** Функции защиты на уровне полей и документов в Elasticsearch платные, поэтому решение построено на том, что чувствительных данных в индексах нет. Защита в четыре слоя:

1. **В приложениях.** Не пишем то, что перечислено в разделе «Чего в логах быть не должно». Записываем только поля из утверждённого списка, тексты исключений очищаем до записи.
2. **В Filebeat.** Оставляем только утверждённые поля, остальные не уходят с инстанса.
3. **В конвейере Elasticsearch.** Значения, похожие на почту, телефон и токен, заменяются маской.
4. **В проверке релиза.** В release QA смотрит записи тестовых заказов, и выполняется поиск по шаблонам персональных данных по индексам.

**Кто имеет доступ.** Вход в Kibana только через прокси с SSO: доступ у сотрудника с действующей учётной записью и нужной ролью, при увольнении учётная запись блокируется. Роли те же, что для Jaeger в [Task3](../Task3/Task3.md).

| Роль                      | Кто                                            | Доступ                                                                                                                                          |
| ------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Поддержка                 | Продакт-менеджер и те, кто разбирает обращения | Чтение `logs-orders-prod`: события заказа и записи о сбоях по заказу без стека. Технические индексы недоступны: в стеках ошибок бывают значения |
| Разработчик               | Java- и C#-разработчики, QA, тимлид            | Чтение всех индексов всех окружений. Менять настройки не могут                                                                                  |
| Администратор логирования | DevOps-инженер                                 | Настройка индексов, политик, ролей, конвейеров и снимков                                                                                        |

Менеджеры по продажам доступа к логам не получают: ответ по заказу клиенту они получают от поддержки. Для каждой роли своё пространство (space) в Kibana.

**Сеть и технические учётные записи.**
- Elasticsearch и Kibana доступны только из внутренней сети. Filebeat отправляет данные по TLS.
- У Filebeat отдельная учётная запись только с правом записи в индексы логов, читать он не может. Учётные записи трейсинга ([Task3](../Task3/Task3.md)) доступа к индексам логов не имеют. У каждого окружения свои токены, чтобы логи dev не попали в prod.
- Сторож логов работает под отдельной учётной записью: чтение `logs-*`, запись `logs-checks-*`. Это отдельный экземпляр сервиса, поэтому учётная запись сторожа трейсинга по-прежнему не читает индексы логов ([Task3](../Task3/Task3.md)), а учётная запись сторожа логов не читает трейсы.
- Токены и пароли хранятся в секретах окружения, а не в коде и не в репозитории.

**Журнал доступа.** Прокси записывает, кто и когда открыл Kibana и какие адреса запрашивал, и журнал попадает в индекс `logs-access-prod`. Содержимое поисковых запросов внутри Kibana так не видно: аудит на стороне Kibana платный. Для разбора инцидентов этого достаточно.

**Хранение и удаление.** Данные не копятся бессрочно: ILM удаляет индексы по сроку. Снимки содержат данные уже удалённых индексов, поэтому срок хранения снимков не должен заметно превышать срок хранения данных. Так как персональных данных в логах нет, отдельной процедуры удаления по запросу не требуется.

**Защита от подделки.** Писать в индексы логов может только учётная запись Filebeat. Данные от внешних клиентов перед записью очищаем от переводов строк и управляющих символов, чтобы клиент не мог подделать запись.

### Размещение

- **Elasticsearch в prod:** один кластер для логов и трейсов. Два узла данных: `node-logs` и `node-traces`, у каждого свой диск. Индексы логов закреплены за первым узлом, индексы трейсов ([Task3](../Task3/Task3.md)) за вторым (фильтрация размещения шардов по атрибуту узла). Третий небольшой узел без данных нужен как арбитр для выборов мастера. В dev и release один узел.
- **Почему так:** объём логов, как правило, заметно больше объёма трейсов. Если логи заполнят диск, Elasticsearch блокирует запись только в индексы на этом узле, и трейсы, а с ними сторож прохождения заказа из Task3, продолжают работать.
- **Реплик в prod нет:** реплика на чужом узле сняла бы изоляцию диска. Отказоустойчивость даёт снимок индексов в S3. Снимки делаем нечасто: компания развивается, нагрузка растёт постепенно, поэтому начинаем с редких снимков (стартово раз в сутки). Частоту повышаем по мере роста числа заказов и нагрузки на логируемые системы: чем больше данных пишется за интервал между снимками, тем больше потеря при падении узла. Снимки храним не дольше самого длинного срока хранения индексов (180 дней). При падении узла мы теряем записи после последнего снимка и восстанавливаем данные из него. Логи можно частично перечитать с инстансов приложений, пока файлы не удалены ротацией. Логи вспомогательные данные, источник истины по заказам — Shop DB и MES db.
- **Filebeat** ставим на каждый инстанс приложения (Shop API, CRM API, MES API), на инстанс RabbitMQ и на инстанс наблюдаемости, где он собирает только журнал прокси. Он отправляет данные на узел логов.
- **Kibana, прокси, Jaeger и сторож логов** работают на одном инстансе наблюдаемости, отдельном от инстансов приложений. Доступ только из внутренней сети.
- **Защита диска логов:** алерт на заполнение диска каждого узла Elasticsearch через Alertmanager ([Task2](../Task2/Task2.md)) по тем же уровням. Узлы Elasticsearch добавляем в мониторинг Task2 так же, как инстансы приложений: метрики сервера и алерт на заполнение диска.
- **Проверка изоляции в release:** заполнить диск узла логов до блокировки записи и убедиться, что запись трейсов продолжается.

## От сбора к анализу

Сбор логов сам по себе тревогу не поднимает: без анализа ошибки по-прежнему обнаруживаются по жалобам клиентов. Нужны два вида анализа: оповещения об известных проблемных ситуациях и поиск необычного поведения. Оба идут через тот же путь оповещений, что в [Task2](../Task2/Task2.md) и [Task3](../Task3/Task3.md): Prometheus и Alertmanager. Так у команды один канал, одни уровни и один порядок реакции.

### Как устроены проверки по логам

Проверки выполняет **сторож логов**: второй экземпляр сервиса сторожа из [Task3](../Task3/Task3.md) со своим набором правил. Сторож, Prometheus и Alertmanager показаны зелёным на [схеме логирования](jewerly_c4_logging.drawio). Сторож трейсинга и общий путь оповещений показаны на [схеме Task3 с мониторингом](../Task3/jewerly_c4_tracing_monitoring.drawio).

- Раз в минуту сторож делает узкие запросы к индексам логов: за короткое окно времени и по типу события (`event.action`). Запросы идут на узел логов, объём выборки небольшой.
- Для каждого правила сторож отдаёт в Prometheus метрику срабатываний с ярлыками `rule` и `service`. `order.id`, `user.id` и `api.client` в ярлыки не идут по той же причине, что в Task2: рядов метрик стало бы неограниченно много.
- Подробности срабатывания (примеры записей, номера заказов, разрез по пользователям и клиентам API) сторож записывает в индекс `logs-checks-<env>` со ссылкой на поиск в Kibana. В тексте алерта есть эта ссылка.
- По метрике срабатывают правила в Alertmanager. Уровни те же: предупреждение — сообщение в канал команды и тикет, критично — дежурному с повтором и эскалацией.

**Почему сторож, а не правила Kibana.**

|                     | Сторож и Alertmanager                                                                     | Правила Kibana                                                   |
| ------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Оповещения          | Один путь для метрик, трейсов и логов, общие уровни и подавление                          | Второй путь оповещений рядом с Alertmanager                      |
| Лицензия            | Не зависит от уровня подписки Elasticsearch                                               | Часть типов правил и подключений платная, состав нужно проверять |
| Стоимость поддержки | Правила пишем и поддерживаем сами, но сервис уже есть и команда его знает (Spring Boot)   | Готовый интерфейс, правила настраиваются без кода                |
| Гибкость            | Любая логика: сравнение с базой, разрез по пользователям, примеры заказов в тексте алерта | Ограничена типами правил                                         |

Kibana остаётся запасным вариантом: если часть простых правил окажется удобнее вести в ней, добавим их туда после проверки состава бесплатного уровня.

### Аномалии

**Нужен ли поиск аномалий.** Да, но простой. Пример из задания: четыре записи о создании заказов, а через секунду десять тысяч. Причины разные: атака конкурентов, ошибка в интеграции клиента API (цикл), сбой. Сколько заказов приходит сейчас, мы не знаем, известен только рост: каждый месяц на 100 заказов больше, чем в предыдущий. Нормальный уровень поэтому меняется плавно, и отклонение в разы видно сравнением с обычным значением. Машинное обучение не нужно: оно платное в Elasticsearch и требует истории данных для обучения.

**Что уже видно без логов.** Всплеск числа заказов заметят метрики Task2 (число запросов и запросов на пользователя, число заказов по статусам) и Task3 (число переходов между статусами). Логи нужны для ответа на вопрос «кто это делает».

| Правило                    | Как проверяем                                                                                                                                                                                                                                                                            | Уровень        | Что делаем                                                                                                                                  |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Всплеск создания заказов   | Число событий создания заказа за минуту втрое выше обычного для этого времени суток и не меньше заданного минимума. Создание заказа: `order.status.changed` со статусом `INITIATED` (магазин) и `api.request.accepted` (API). Минимум нужен, чтобы не срабатывать на рост с нуля до трёх | Критично       | В тексте алерта сторож даёт топ пользователей (`user.id`) и клиентов API (`api.client`) за окно. Поддержка проверяет, легитимен ли источник |
| Заказы от одного источника | Больше половины событий создания за окно приходится на один `user.id` или `api.client`, при этом событий не меньше заданного минимума                                                                                                                                                    | Предупреждение | Проверить, не автоматизированный ли это клиент или ошибка интеграции                                                                        |
| Отказы клиента API         | Число `api.request.rejected` за окно втрое выше обычного, с разрезом по `api.client`                                                                                                                                                                                                     | Предупреждение | Связаться с клиентом: возможно, у него сломана интеграция                                                                                   |

**Что делаем при срабатывании.** Проверить источник по разрезу из алерта. Если атака подтверждается, эскалация тимлиду и временная блокировка учётной записи средствами приложения. Постоянная защита (ограничение частоты запросов на входе) в это решение не входит: на схеме нет слоя, где её можно включить.

**Ограничение.** IP-адреса мы не логируем: это персональные данные, а слоя на входе, который их фиксировал бы, нет. Поэтому распределённую атаку с многих адресов от органического всплеска по логам не отличить, разрез идёт по пользователю и клиенту API.

### Дашборды Kibana

- **История заказа:** события по `order.id` из `logs-orders` в порядке времени, включая записи о сбоях по заказу. Основной инструмент поддержки.
- **Ошибки по системам:** ERROR и WARN по `service.name` и `event.action`. Для разработчиков.
- **Срабатывания правил:** таблица из `logs-checks-<env>`: какое правило, когда, для каких заказов.

Права по ролям те же, что описаны в разделе «Политика безопасности»: поддержка видит только историю заказа.

### Как не дублировать мониторинг из Task2 и Task3

| Вопрос                                                     | Метрики ([Task2](../Task2/Task2.md))              | Трейсы ([Task3](../Task3/Task3.md))    | Логи                                           |
| ---------------------------------------------------------- | ------------------------------------------------- | -------------------------------------- | ---------------------------------------------- |
| Доля ошибок HTTP, задержки                                 | Да                                                | Только по шагам заказа                 | Не дублируем                                   |
| Сообщение не получено или не обработано                    | Dead-letter-очередь, возраст сообщения            | Сторож: публикация есть, получения нет | Не дублируем. В алерте по ссылке видна причина |
| Где остановился заказ                                      | Возраст заказа в статусе                          | Сторож: на каком переходе              | Не дублируем                                   |
| Причина конкретной ошибки (файл не найден, ошибка расчёта) | Нет                                               | Нет                                    | Алерты по событиям                             |
| Невозможный переход статуса, дубликаты сообщений           | Нет                                               | Нет                                    | Алерты по событиям                             |
| Частые перезапуски                                         | Метрика доступности не ловит короткие перезапуски | Нет                                    | Алерт по `app.started`                         |
| Всплеск создания заказов                                   | Замечают                                          | Замечают                               | Показывают, кто создаёт                        |
| Логи перестали поступать                                   | Нет                                               | Нет                                    | Алерт «Логи не поступают»                      |

Чтобы одна проблема не порождала лавину алертов, в Alertmanager настраиваем подавление: пока горят «Компонент недоступен» из Task2, «Трейсинг не получает данные» из Task3 или «Логи не поступают», алерты сторожа логов по затронутому сервису не отправляются, причина уже известна.

## Выбор технологии

Elasticsearch уже назван хранилищем трейсов в [Task3](../Task3/Task3.md), и для логов мы выбираем его же. Сравнение ниже объясняет, почему это оправдано и чем мы за это платим. Сведения о лицензиях и возможностях проверены по документации производителей в сентябре 2026 года, источники в конце раздела.

Кандидаты: Elasticsearch с Kibana и Beats (ELK), OpenSearch (близкий по классу вариант), Splunk (коммерческий стандарт) и Grafana Loki (дешёвое хранение логов, работает в паре с Prometheus и Grafana из [Task2](../Task2/Task2.md)).

### Итог

**Выбираем Elasticsearch.** Причины:
- трейсы уже хранятся в Elasticsearch ([Task3](../Task3/Task3.md)), поэтому логи и трейсы живут в одном кластере с одним языком запросов, а переход по trace id проще всего;
- Filebeat и Kibana работают с ним без обходных решений;
- главный сценарий, поиск всего по номеру заказа, для полнотекстового индекса быстрый;
- всё нужное решению входит в бесплатный уровень;
- стек изучен, к нему много документации.

**Почему не остальные.**
- **OpenSearch** — сильный кандидат по лицензии, безопасности и управляемому сервису. Отказались из-за совместимости: современный Filebeat с ним не работает, и пришлось бы менять решение Task3.
- **Splunk** — платный по объёму данных, бесплатная версия не годится, бюджет не указан, а трейсы всё равно остались бы в Elasticsearch.
- **Loki** — самое дешёвое хранение, но поиск по номеру заказа медленнее, и для трейсов всё равно нужен Elasticsearch.

**Чем платим и как это компенсируем.**

| Минус                                                                                          | Как компенсируем                                                                                                                                              |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Управляемого Elasticsearch в Yandex Cloud нет, кластер эксплуатируем сами, а DevOps один       | Минимальная топология (два узла данных и арбитр), снимки в S3, алерты на диск, документированная процедура восстановления                                     |
| Платные функции недоступны: аудит, защита на уровне полей, машинное обучение, часть оповещений | Решение построено без них: чувствительных данных в индексах нет, доступ фиксирует прокси, оповещения идут через сторож и Alertmanager, аномалии ищем порогами |
| Индекс по всем полям тяжелее исходных данных                                                   | Минимум записей, разные сроки хранения, размер оцениваем формулой, метрика «объём логов на 100 заказов»                                                       |

**Когда пересмотрим выбор.**
- Эксплуатация кластера станет неподъёмной для команды: рассмотрим OpenSearch как управляемый сервис Yandex Cloud, тогда придётся заменить сборщик и обновить Task3.
- Стоимость хранения логов станет главной проблемой: рассмотрим Loki для логов при сохранении Elasticsearch для трейсов.
- Понадобится аудит или защита на уровне полей: платный уровень Elasticsearch или OpenSearch.
