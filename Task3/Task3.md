# «Архитектурное решение по трейсингу»

Документ опирается на условие, [схему C4](../jewerly_c4_model.drawio) и допущения из [README](../README.md) (Д1–Д8).

## Анализ системы

Задача трейсинга — ответить на два вопроса по конкретному заказу: что с ним происходило и где он сейчас. Метрики из [Task2](../Task2/Task2.md) показывают, что заказы зависают и сколько их. Трейсинг должен показать, на каком шаге и в какой системе это случилось.

### Путь заказа

Заказ проходит через три приложения, очередь и людей. По статусам из условия и допущениям путь выглядит так:

| Шаг | Статус                                                                     | Где происходит                                                                   | Как передаётся дальше                                         |
| --- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1   | `INITIATED`, `FILE_UPLOADED`, `SUBMITTED`                                  | Shop API: запись в Shop DB, файл в S3                                            | Через Shop DB: CRM API находит заказ опросом (Д1)             |
| 2   | —                                                                          | CRM API публикует `order.submitted` с ключом файла (Д2)                          | Сообщение RabbitMQ                                            |
| 3   | `PRICE_CALCULATED`                                                         | MES API читает файл из S3, считает цену (Д3)                                     | Сообщение RabbitMQ в CRM (Д6)                                 |
| 3а  | `PRICE_CALCULATED` (заказ API-клиента)                                     | MES API принимает запрос клиента, считает цену. Клиент опрашивает результат (Д6) | Сообщение RabbitMQ, CRM создаёт заказ                         |
| 4   | `MANUFACTURING_APPROVED`                                                   | CRM: продавец подтверждает заказ                                                 | Сообщение RabbitMQ в MES                                      |
| 5   | `MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING`, `SHIPPED` | MES: оператор берёт заказ, выполняет, упаковывает, отправляет                    | Сообщения RabbitMQ в CRM, CRM обновляет статус в Shop DB (Д7) |
| 6   | `CLOSED`                                                                   | CRM: по сообщению транспортной компании или вручную                              | Запись в Shop DB                                              |

Между шагами 1 и 6 проходят недели: обещанный срок — три недели, а на шагах 4 и 5 заказ ждёт людей часами и днями.

### Где заказ может сломаться или зависнуть

| Место                                      | Основание | Что может случиться с заказом                                                                                                          | Что должен показать трейсинг                                                                        |
| ------------------------------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Оформление в Shop API                      | Условие   | Ошибка записи в Shop DB или загрузки файла в S3: заказ не доходит до `SUBMITTED`, покупатель видит ошибку или повторяет попытку        | На каком обращении (Shop DB, S3) произошла ошибка и какая                                           |
| Опрос Shop DB со стороны CRM API           | Д1        | Опрос остановился или падает на конкретном заказе: заказ остаётся в `SUBMITTED` и никуда не уходит                                     | Что опрос нашёл заказ, сколько заказ ждал и чем закончилась передача                                |
| Публикация `order.submitted`               | Д2, Д5    | Статус в Shop DB обновлён, а сообщение не отправлено, или наоборот. Гарантий доставки нет                                              | Была ли публикация и подтвердил ли её брокер                                                        |
| Приём сообщения в MES и расчёт цены        | Д2, Д3    | MES не находит файл в S3, расчёт падает или идёт дольше 30 минут из-за конкуренции с дашбордом и API-клиентами в одном инстансе        | Когда сообщение получено, сколько шёл расчёт, чем закончился, сколько ждал до начала                |
| Сообщения между CRM и MES на любом шаге    | Д5, Д7    | Сообщение потеряно или не обработано: статус изменился в одной базе, а в другой нет                                                    | Цепочку «опубликовано → получено → обработано». Отсутствие получения трейс сам не покажет, см. ниже |
| Заказ API-клиента                          | Д6        | Расчёт выполнен, но сообщение в CRM не дошло: клиент видит цену, а заказа в CRM нет. Или клиент опрашивает результат и получает ошибку | Связь идентификатора запроса клиента с заказом и все опросы клиента по этому запросу                |
| Подтверждение продавцом и работа оператора | Условие   | Заказ ждёт человека. Это нормально, пока ожидание укладывается в срок, но действие человека может не дойти до другой системы           | Когда было действие, какая система его приняла и дошло ли сообщение                                 |
| Закрытие заказа                            | Условие   | Сообщение от транспортной компании не пришло, заказ остаётся в `SHIPPED`                                                               | Получено ли сообщение от транспортной компании и чем закончилась его обработка                      |

### Разрывы контекста

Трейс связывает шаги, пока они вызывают друг друга и передают контекст трейса. В нашей системе цепочка вызовов рвётся в нескольких местах. Без решения для каждого разрыва мы получим набор несвязанных фрагментов, а не путь заказа.

| Разрыв                           | Основание | Почему теряется связь                                                                                        |
| -------------------------------- | --------- | ------------------------------------------------------------------------------------------------------------ |
| Опрос Shop DB со стороны CRM API | Д1        | Заказ передаётся через запись в базе, а не через вызов. Контекст запроса покупателя в базе не сохраняется    |
| Сообщения RabbitMQ               | Д2, Д4    | Контекст автоматически не переносится. Если его не положить в заголовки сообщения, шаги CRM и MES не связать |
| Действия людей                   | Условие   | Продавец и оператор действуют через часы и дни, каждый их запрос — новый трейс без связи с предыдущим шагом  |
| Опросы API-клиентов              | Д6        | Каждый опрос результата — отдельный HTTP-запрос. Связь с заказом есть только через идентификатор запроса     |
| Транспортная компания            | Условие   | Внешняя система вне схемы. Её сообщение приходит без нашего контекста                                        |
| Потеря сообщения                 | Д5        | Трейс фиксирует то, что произошло. Если сообщение опубликовано, но не получено, спана получения просто нет   |

Общий вывод: сквозной трейс «от покупателя до закрытия» построить нельзя. Заказ живёт неделями, а по пути несколько разрывов. Поэтому шаги связываем общим атрибутом `order.id` (сквозного идентификатора сейчас нет, Д4). Внутри шага, где вызовы идут подряд (например, приём сообщения, расчёт, публикация результата), контекст передаём обычным способом. Как именно это устроено, описано в разделе «Предлагаемое решение».

### Системы, которые покрываем трейсингом

| Объект схемы                             | Покрытие                                | Что видим                                                                                                                                 | Очередь               |
| ---------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| CRM API                                  | Полное                                  | Опрос Shop DB, публикация и приём сообщений, запросы продавцов, приём сообщения транспортной компании, обращения к Shop DB и S3           | 1                     |
| MES API                                  | Полное                                  | Приём и публикация сообщений, расчёт цены одним спаном, запросы API-клиентов и их опросы, действия операторов, запрос списка заказов (Д8) | 1                     |
| RabbitMQ                                 | Частичное: спаны публикации и получения | Брокер изнутри не инструментируем. Путь сообщения видим со стороны CRM API и MES API, контекст передаём в заголовках                      | 1                     |
| Shop API                                 | Полное                                  | Запросы покупателей, смена статусов до `SUBMITTED`, обращения к Shop DB и S3                                                              | 2                     |
| Shop DB, MES db                          | Частичное: спаны на стороне приложений  | Управляемый сервис, изнутри не инструментируем. Видим запросы к базе, их длительность и ошибки                                            | Вместе с приложениями |
| Хранилище 3D-файлов                      | Частичное: спаны на стороне приложений  | Видим загрузку и чтение файла, длительность и ошибки. Важно для расчёта цены: MES должен найти файл (Д2)                                  | Вместе с приложениями |
| Internet Shop, CRM, MES (веб-интерфейсы) | Не покрываем на старте                  | Действия пользователей видны как запросы к API. Трейсинг из браузера откладываем, см. раздел «Компромиссы»                                | —                     |
| API-клиенты, транспортная компания       | Не покрываем, внешние системы           | Трейс начинается на нашей стороне, в MES API и CRM API. Контекст от внешних систем не принимаем                                           | —                     |

Порядок выбран по месту потерь. Условие говорит о теряющихся сообщениях и о жалобах API-клиентов, а это участок CRM API → RabbitMQ → MES API и обратно. Shop API подключаем вторым: оформление в магазине пользователь видит сам, и ошибки там заметнее. Спаны баз и хранилища появляются вместе с инструментацией приложений и отдельной работы почти не требуют.

Схема с выделенными системами: [jewerly_c4_tracing.drawio](jewerly_c4_tracing.drawio). Сплошная оранжевая рамка означает полное покрытие, пунктирная — частичное.

### Данные в трейсинге

Для технических атрибутов используем стандартные имена OpenTelemetry, для атрибутов заказа вводим свои.

| Группа           | Данные                                                                                                                                                                          | Зачем                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Где выполнено    | Сервис (`service.name`), версия (`service.version`), окружение (`deployment.environment`: dev, release, prod), инстанс                                                          | Отличить сервисы и окружения. По версии видно, после какого релиза начались проблемы |
| Идентификаторы   | Trace id, span id, `order.id`, идентификатор сообщения RabbitMQ, идентификатор запроса расчёта (Д6), `api.client` для внешнего API                                              | Найти все шаги заказа и связать опросы API-клиента с заказом                         |
| Шаг заказа       | Статус «из» и «в» (`order.status.from`, `order.status.to`), система, которая меняет статус (Д7), источник заказа (`order.source`: `shop`, `api`)                                | Видеть, какой переход сделан и где                                                   |
| Сообщения        | Очередь и ключ маршрутизации, тип сообщения (`order.submitted` и другие, Д4), операция (публикация, получение), признак повторной доставки, результат (подтверждено, отклонено) | Проследить сообщение от публикации до обработки, заметить повторы и отказы           |
| HTTP и обращения | Метод, шаблон маршрута (`/orders/{id}`, а не конкретный URL), код ответа, тип вызывающего (`operator`, `api_client`), тип операции с базой и таблица, операция с S3             | Понять, какой вызов упал или затормозил                                              |
| Время            | Длительность спана, время ожидания перед шагом (например, сколько заказ пролежал в `SUBMITTED` до передачи в MES, Д1), длительность расчёта цены (Д3)                           | Найти, где заказ провёл больше всего времени                                         |
| Результат        | Успех или ошибка, тип ошибки, короткое сообщение об ошибке без данных пользователя                                                                                              | Понять, чем закончился шаг                                                           |

**Чего в трейсинге быть не должно:**

- персональные данные покупателей: имя, телефон, почта, адрес доставки. Идентификатор покупателя тоже не добавляем: заказ находится по `order.id`, а покупателя по заказу можно найти в CRM. В метриках [Task2](../Task2/Task2.md) для RPS на пользователя используется внутренний идентификатор покупателя (псевдоним): там он нужен, чтобы найти источник нагрузки. В трейсах он не нужен;
- тела запросов, ответов и сообщений целиком;
- содержимое 3D-файлов. Ключ файла допустим, если в нём нет данных пользователя;
- токены, пароли, заголовки `Authorization` и cookie, параметры запросов с секретами;
- значения параметров в SQL-запросах: оставляем только тип операции и таблицу;
- коммерческие данные: цены и условия для API-клиентов. Для поиска заказа они не нужны.

Как эти ограничения обеспечиваются технически, описано в разделе «Безопасность».

### Чем трейсинг отличается от метрик и логов

| Инструмент                           | На какой вопрос отвечает                                | Пример                                                                                |
| ------------------------------------ | ------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Метрики ([Task2](../Task2/Task2.md)) | Сколько и как быстро, в целом по системе                | 12 заказов дольше часа в `SUBMITTED`, очередь к MES растёт                            |
| Трейсы                               | Где конкретный заказ и сколько времени занял каждый шаг | Заказ 1042: опрос нашёл его через 3 минуты, сообщение опубликовано, в MES не получено |
| Логи ([Task4](../Task4/Task4.md))    | Что именно произошло внутри шага                        | Текст ошибки и контекст, при котором MES не смог прочитать файл                       |

Инструменты дополняют друг друга. Метрика сигнализирует о проблеме, трейс показывает место, лог объясняет причину. Для перехода между ними trace id записываем в логи.

**Пересечение с метриками Task2.** Метрики «число заказов по статусам» и «возраст самого старого заказа в статусе» берутся из баз и уже показывают, что заказы зависли. Трейсинг их не заменяет и не дублирует. Он добавляет то, чего в базах нет: на каком переходе между системами остановился конкретный заказ (опрос, публикация, получение, обработка) и сколько длился каждый шаг. Автоматический мониторинг по данным трейсинга (раздел «Предлагаемое решение») строим на этих переходах, а не на возрасте статуса, чтобы не дублировать алерты Task2.

## Мотивация

Сейчас на вопрос «где заказ и что с ним было» команда отвечает вручную: сверяет Shop DB и MES db, ищет сообщение в очереди, спрашивает продавцов и операторов. Трейсинг даёт ответ по номеру заказа за минуты и показывает, на каком шаге и в какой системе заказ остановился.

### Что происходит сейчас

- **Заказы «непонятно где».** По условию команда видит, что заказы находятся в непонятном состоянии или зависают внутри ИТ-ландшафта. Заказ проходит через три приложения, очередь и двух людей, а статусы хранятся в двух базах, и единого источника истины нет (Д7). Сквозного идентификатора нет (Д4), поэтому связать шаги одного заказа можно только вручную.
- **Сообщения теряются незаметно.** Гарантий доставки в интеграции через RabbitMQ нет (Д5). Потерянное сообщение не оставляет следа: одна система считает, что заказ передан, другая о нём не знает.
- **Разбор идёт со слов клиента.** Клиенты жалуются, что над заказом работают месяцами вместо трёх недель. API-клиенты ежедневно сообщают, что не получили заказы. Ответить им по фактам сейчас нечем: где именно застрял конкретный заказ, никто не видит.
- **Последствия уже дорогие.** Через месяц после открытия API компания потеряла несколько крупных контрактов, растёт недовольство B2C-клиентов. Заказов с каждым месяцем больше, и ручной разбор будет занимать всё больше времени.
- **Мониторинг скажет «что», но не «где».** Метрики из [Task2](../Task2/Task2.md) покажут, что в `SUBMITTED` висит десяток заказов или что очередь растёт. Какой шаг не прошёл для конкретного заказа и почему, по агрегатам не понять.

### Что даст трейсинг компании

| Что даёт                            | Как это выглядит на практике                                                                                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| История заказа по номеру            | По `order.id` видно все шаги: когда опрос нашёл заказ, когда ушло сообщение, когда MES его получил, сколько шёл расчёт, кто и когда подтвердил. Ответ на «где заказ» без ручной сверки баз |
| Место, где заказ остановился        | Видно последний выполненный шаг и следующий, которого не было. Например, сообщение опубликовано, но не получено — значит, проблема в доставке, а не в MES или у оператора                  |
| Ответ клиенту фактами               | Поддержка и менеджеры по продажам получают конкретный ответ: на каком этапе заказ и что с ним случилось. Для API-клиента — по идентификатору его запроса (Д6)                              |
| Меньше нагрузки на разработчиков    | Первичный разбор делает поддержка по трейсу. Разработчики подключаются, когда место уже найдено, и сразу переходят к логам ([Task4](../Task4/Task4.md)) по trace id                        |
| Узкие места по фактам               | Длительность каждого шага показывает, где заказ проводит больше всего времени: ожидание опроса (Д1), очередь, расчёт цены (Д3) или ожидание людей. Это основа для решений по оптимизации   |
| Основа для автоматического контроля | Из данных трейсинга строится проверка прохождения заказа и алерты на «не случившийся» шаг (раздел «Предлагаемое решение»)                                                                  |

Трейсинг сам заказы не ускоряет и потери сообщений не устраняет. Он показывает, где именно проблема, и сокращает время на её поиск. Исправления, например гарантии доставки в интеграции, остаются отдельной работой.

### Почему это стоит ресурсов команды

- **Ручной поиск уже обходится дорого.** Каждый разбор жалобы требует сверки двух баз и опроса людей, а жалоб становится больше вместе с числом заказов.
- **Вложение умеренное.** OpenTelemetry и Jaeger — открытый код, без лицензий. Для Spring Boot есть автоинструментация без изменения кода, для MES API на C# — SDK, исходники MES у компании есть. Основная ручная работа — передача контекста через сообщения и атрибуты заказа.
- **Используем то, что уже внедряется.** Хранилище на Elasticsearch согласуется с решением по логам ([Task4](../Task4/Task4.md)), алерты и дашборды идут через Alertmanager и Grafana из [Task2](../Task2/Task2.md). Отдельный стек с нуля не нужен.
- **Внедрять можно по частям.** Сначала участок, где теряются заказы (CRM API, RabbitMQ, MES API), затем Shop API. Польза появляется уже после первого этапа.

### Метрики решения

Базовых значений сейчас нет, поэтому числа не задаём. Для каждой метрики указано, как её считать и откуда брать данные. Значения «до» берём из журнала инцидентов, который начинает вести команда по плану [Task2](../Task2/Task2.md) (задача 17), до запуска трейсинга в prod. Значения «после» сравниваем через первые недели работы трейсинга.

| Метрика                                                   | Тип         | Как считаем                                                                                                                          | Откуда данные                                             | Как влияет трейсинг                                                                                                  |
| --------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Время локализации проблемы с заказом                      | Техническая | Медиана времени от сигнала (жалоба или алерт) до ответа «на каком шаге и в какой системе заказ». Отдельно для заказов магазина и API | Журнал инцидентов: отметки «сигнал» и «место найдено»     | Главный эффект: вместо ручной сверки баз — поиск по `order.id`. Ожидаем снижение                                     |
| Доля заказов с полностью видимым путём                    | Техническая | Число заказов, у которых в трейсинге есть все ожидаемые шаги до текущего статуса, делённое на число заказов за период                | Хранилище трейсов, сверка со статусами в Shop DB и MES db | Показывает полноту самого решения. Заказы с «дырами» указывают на пропущенные разрывы контекста или потерю сообщений |
| Доля обращений, разобранных без привлечения разработчиков | Бизнес      | Число обращений клиентов по заказам, на которые поддержка ответила сама, делённое на все такие обращения                             | Журнал инцидентов или тикеты поддержки                    | Поддержка находит место по трейсу сама. Ожидаем рост доли и меньше отвлечений команды разработки                     |
| Жалобы на несданные и просроченные заказы на 100 заказов  | Бизнес      | Число жалоб клиентов магазина и API-клиентов за месяц, делённое на число заказов за месяц и умноженное на 100. Отдельно по B2C и API | Обращения к менеджерам по продажам, число заказов из CRM  | Косвенно: быстрее находим и чиним причины зависаний. Считаем на 100 заказов, потому что их число растёт каждый месяц |
| Доля заказов, выполненных в обещанный срок                | Бизнес      | Число заказов, у которых от `SUBMITTED` до `SHIPPED` прошло не больше трёх недель, делённое на число отправленных заказов за период  | Статусы в Shop DB, длительности шагов из трейсинга        | Косвенно: видно, на каком шаге заказы теряют время, и исправления направляются туда                                  |

Первые две метрики показывают, работает ли сам трейсинг. Три оставшиеся показывают, что он даёт бизнесу. Две последние зависят не только от трейсинга, но и от исправлений, которые он помогает найти, поэтому оцениваем их вместе с этими исправлениями.

## Предлагаемое решение

Схема решения: [jewerly_c4_tracing.drawio](jewerly_c4_tracing.drawio). Новые компоненты и связи выделены красным, системы, которые покрываем трейсингом, — оранжевой рамкой.

### Технологии

| Компонент             | Технология                                                  | Роль                                                                                                                                                                                                                  |
| --------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Инструментация Java   | OpenTelemetry Java agent и API                              | Shop API и CRM API (Spring Boot). Агент без изменения кода создаёт спаны для HTTP, JDBC, RabbitMQ и S3. Атрибуты заказа и свои спаны добавляем через API                                                              |
| Инструментация C#     | OpenTelemetry .NET SDK                                      | MES API. Готовые инструментации для ASP.NET Core, HttpClient, Npgsql и AWS SDK (S3). Спаны RabbitMQ и расчёта цены добавляем в коде, исходники MES есть                                                               |
| Приёмник и обработчик | OpenTelemetry Collector                                     | Единая точка приёма спанов от трёх API по OTLP. Чистит атрибуты, сэмплирует, передаёт в Jaeger. Позже из него же берём метрики для мониторинга                                                                        |
| Просмотр и поиск      | Jaeger                                                      | Интерфейс поиска трейсов, в том числе по `order.id`. Записывает спаны в хранилище и читает из него                                                                                                                    |
| Доступ к Jaeger       | Обратный прокси с входом через SSO (например, OAuth2 Proxy) | Единственная точка входа в Jaeger: вход по корпоративной учётной записи, роли, свой адрес для каждого окружения, журнал доступа (раздел «Безопасность»)                                                               |
| Хранилище             | Elasticsearch                                               | Хранение и поиск спанов. Один кластер для логов и трейсов, у трейсов свой узел данных со своим диском. Обоснование выбора и раздел «Размещение» — в [Task4](../Task4/Task4.md) |

Почему так:

- OpenTelemetry — открытый стандарт с поддержкой и Java, и .NET. Инструментация не привязана к Jaeger: если сменим хранилище или интерфейс, код приложений не меняется.
- Collector отделяет приложения от хранилища. Чистка персональных данных и сэмплирование настраиваются в одном месте, а не в трёх приложениях на двух языках.
- Jaeger — открытый код, умеет искать по атрибутам и работает с Elasticsearch. Это тот же движок, что и для логов, команде не нужно осваивать второе хранилище.

### Инструментация приложений

Автоматическая инструментация даёт технические спаны: запросы, обращения к базам, очереди и S3. Этого мало, чтобы видеть путь заказа, поэтому в каждом приложении добавляем в коде:

| Что добавляем                                                    | Где                             | Зачем                                                                                                               |
| ---------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Атрибут `order.id` на спанах шага                                | Shop API, CRM API, MES API      | Главный ключ поиска: все шаги заказа находятся по номеру                                                            |
| Спан смены статуса `order.status.change` с атрибутами «из» и «в» | Везде, где меняется статус (Д7) | Каждый переход виден отдельной записью. По имени спана легко искать и считать переходы                              |
| Спан цикла опроса Shop DB и спан передачи каждого заказа         | CRM API                         | Видно, что опрос работает, какие заказы нашёл и сколько каждый ждал в `SUBMITTED` (Д1)                              |
| Один спан на весь расчёт цены                                    | MES API                         | Длительность и результат расчёта (Д3). Внутри расчёта спаны не создаём: расчёт и так нагружает единственный инстанс |
| Атрибуты `api.client` и идентификатор запроса расчёта            | MES API                         | Связывают запросы и опросы API-клиента с заказом (Д6)                                                               |
| Trace id в каждой строке лога                                    | Три API                         | Переход от трейса к логам ([Task4](../Task4/Task4.md)) и обратно                                                    |

### Передача контекста

Для каждого разрыва из раздела «Анализ системы» выбран свой способ.

| Разрыв                                               | Решение                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сообщения RabbitMQ                                   | Публикующая сторона кладёт контекст в заголовок сообщения (`traceparent`, стандарт W3C Trace Context). Получатель достаёт его и продолжает тот же трейс. Так шаг «действие в одной системе → сообщение → обработка в другой» виден одним трейсом. В Java это делает агент, в MES API добавляем в код публикации и получения                                      |
| Опрос Shop DB (Д1)                                   | При переходе заказа в `SUBMITTED` Shop API записывает `traceparent` текущего запроса в новое поле записи заказа. CRM API при опросе читает его и создаёт спан передачи заказа со ссылкой (span link) на спан покупателя. Из трейса передачи можно перейти к оформлению заказа. Стоимость доработки небольшая: одно необязательное поле в таблице заказов Shop DB |
| Расчёт цены для API-клиента (Д6)                     | MES API отвечает клиенту сразу, а расчёт идёт позже. Спан расчёта связываем со спаном запроса ссылкой (span link), чтобы не держать трейс запроса открытым до 30 минут                                                                                                                                                                                           |
| Опросы результата API-клиентами (Д6)                 | Каждый опрос — отдельный короткий трейс с идентификатором запроса и `api.client`, а когда заказ создан, ещё и с `order.id`. Все опросы клиента находятся по идентификатору запроса                                                                                                                                                                               |
| Действия людей                                       | Каждое действие продавца или оператора начинает новый трейс с `order.id`. Связь с предыдущими шагами — через этот атрибут                                                                                                                                                                                                                                        |
| Внешние системы (API-клиенты, транспортная компания) | Входящий контекст от них не принимаем: MES API и CRM API начинают свой трейс. Иначе внешняя сторона может подменить trace id или навязать сэмплирование. Способ отбрасывать входящий контекст на внешних маршрутах выберем при внедрении (задача в разделе «Безопасность»)                                                                                       |

### Связь шагов заказа во времени

Заказ живёт неделями, поэтому один трейс на весь заказ не делаем. Трейс соответствует одному шагу: действию и всему, что оно запустило (сообщения, обработку в другой системе). Все трейсы заказа связаны атрибутом `order.id`, в Jaeger они находятся поиском по нему.

Почему так, а не один длинный трейс:

- Интерфейсы и хранилища трейсинга рассчитаны на трейсы длиной в секунды и минуты. Трейс на недели неудобно смотреть, а сэмплирование по целому трейсу становится невозможным.
- Спан, открытый неделями, теряется при перезапуске приложения, а у каждого приложения один инстанс.
- Чтобы связать все шаги ссылками, пришлось бы хранить контекст на каждом шаге в обеих базах. Атрибут `order.id` даёт тот же поиск без изменений в хранении. Ссылки используем только там, где контекст сохраняется дёшево: опрос Shop DB и расчёт цены.

### Сэмплирование

Запросов к каталогу, дашборду и health-check заметно больше, чем заказов: заказ — это несколько шагов, а остальные запросы идут постоянно. Решение о сохранении принимает Collector по завершённому трейсу (tail sampling). Приложения отправляют все спаны.

| Трейсы                                          | Решение                                             |
| ----------------------------------------------- | --------------------------------------------------- |
| С атрибутом `order.id`                          | Сохраняем все                                       |
| С ошибкой                                       | Сохраняем все                                       |
| Медленные (дольше порога для маршрута)          | Сохраняем все. Пороги стартовые, уточняем по данным |
| Health-check                                    | Отбрасываем                                         |
| Остальные (каталог, дашборд без ошибок и т. п.) | В prod стартово 10%, в dev и release все            |

Расчёт цены длится до 30 минут, и его спан завершается позже, чем Collector принимает решение по трейсу. Collector запоминает решение по trace id, поэтому поздние спаны попадают в уже сохранённый трейс. Атрибут `order.id` ставим на первый спан шага, чтобы решение «сохранить» принималось сразу.

### Хранение

| Данные                  | Срок хранения (стартовый) | Почему                                                                                                                             |
| ----------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Трейсы заказов (prod)   | 180 дней                  | Заказ живёт недели, а зависшие «висят месяцами». Историю нужно видеть до закрытия заказа и какое-то время после, для разбора жалоб |
| Остальные трейсы (prod) | 14 дней                   | Нужны для разбора недавних ошибок и задержек, потом теряют ценность                                                                |
| dev и release           | 7 дней                    | Нужны для проверки инструментации и релиза                                                                                         |

Трейсы заказов и остальные Collector отправляет раздельно, по наличию `order.id`, и они хранятся в разных индексах Elasticsearch со своей политикой жизненного цикла (ILM). Индексы трейсов закреплены за узлом трейсов, индексы логов ([Task4](../Task4/Task4.md)) за узлом логов, у каждого своя политика жизненного цикла. Объём трейсов заказов небольшой, основной объём дают остальные трейсы, и его регулируем долей сэмплирования. Размер хранилища оцениваем по данным dev и release до выката в prod.

### Размещение

- Collector, Jaeger и прокси доступа ставим на отдельный инстанс EC2, не на инстансы приложений: сбой приложения не должен отключать трейсинг, и наоборот. Доступ только из внутренней сети.
- Elasticsearch: один кластер для логов и трейсов ([Task4](../Task4/Task4.md)). В prod у трейсов свой узел данных `node-traces` со своим диском, у логов свой: переполнение диска логами не блокирует запись трейсов и не оставляет без данных сторож. Реплик нет, отказоустойчивость даёт снимок индексов в S3, стартово раз в сутки. В dev и release один узел.
- prod отделён от dev и release: свой Collector и свои индексы. Данные prod не смешиваются с тестовыми, и доступ к ним можно ограничить отдельно.
- Сторож прохождения заказа работает на том же инстансе, что Collector и Jaeger, а не на инстансах приложений. Он лёгкий: запрос к Elasticsearch раз в 5 минут по узкому окну времени. Так он не отбирает ресурсы у единственных экземпляров приложений. Prometheus следит за его доступностью, недоступность вызывает алерт «Компонент недоступен» из [Task2](../Task2/Task2.md).
- Если Collector недоступен, приложения теряют спаны, но продолжают работать: отправка спанов асинхронная и не блокирует обработку заказов.

### План внедрения

| 3    | Инструментировать Shop API: агент, атрибуты заказа, поле `traceparent` в записи заказа Shop DB, span link в CRM API                                                     | Java-разработчики                 |

### Автоматический мониторинг прохождения заказа и алертинг

Схема с элементами мониторинга: [jewerly_c4_tracing_monitoring.drawio](jewerly_c4_tracing_monitoring.drawio). Новые элементы этого подраздела выделены зелёным, элементы трейсинга остаются красными.

Трейсинг хорошо показывает то, что произошло. Зависший заказ — это как раз то, что **не** произошло: сообщение опубликовано, но не получено, статус сменился в MES, но не в CRM. Поэтому автоматический контроль строим из двух частей: метрики из спанов показывают, как идёт поток в целом, а отдельный сервис-«сторож» ищет конкретные заказы, у которых нет ожидаемого следующего шага.

#### Метрики из спанов

В Collector включаем расчёт метрик из спанов (spanmetrics). Он считает число спанов, долю ошибок и распределение длительности, а Prometheus из [Task2](../Task2/Task2.md) забирает эти метрики.

| Метрика                          | Из каких спанов                                   | Ярлыки                                                            | Что показывает                                                                                            |
| -------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Число переходов между статусами  | `order.status.change`                             | `service`, `order.status.from`, `order.status.to`, `order.source` | Сколько заказов проходит каждый переход в час. Резкое падение на одном переходе — там что-то остановилось |
| Доля ошибок на шаге              | Обработка сообщений, опрос Shop DB, расчёт цены   | `service`, имя спана, очередь                                     | На каком шаге и в каком сервисе заказы падают с ошибкой                                                   |
| Длительность шага                | Обработка сообщений, расчёт цены, передача заказа | `service`, имя спана, `order.source`                              | Сколько занимает каждый шаг, отдельно для магазина и API                                                  |
| Публикации и получения сообщений | Спаны публикации и получения RabbitMQ             | `service`, очередь, тип сообщения                                 | Сравнение потоков: публикаций больше, чем получений, при пустой очереди — признак потери (Д5)             |

`order.id` в ярлыки не идёт по той же причине, что и в Task2: каждый заказ добавлял бы новый ряд метрик. Отдельные заказы ищет сторож.

#### Сторож прохождения заказа

Небольшой сервис на Spring Boot (стек, который команда знает). Раз в 5 минут он читает трейсы заказов из Elasticsearch и проверяет, что за каждым шагом в срок последовал ожидаемый следующий.

Проверки по логам выполняет отдельный экземпляр этого сервиса со своей учётной записью, он описан в [Task4](../Task4/Task4.md), раздел «От сбора к анализу».

| Проверка                                      | Начало                                                                  | Ожидаемый следующий шаг                                        | Срок (стартовый) | Основание |
| --------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------- | --------- |
| Сообщение к MES не получено                   | Спан публикации в CRM API (`order.submitted`, `MANUFACTURING_APPROVED`) | Спан получения этого сообщения в MES API                       | 60 минут         | Д2, Д5    |
| Сообщение к CRM не получено                   | Спан публикации в MES API (цена, смена статуса)                         | Спан получения в CRM API                                       | 15 минут         | Д5, Д6    |
| Сообщение получено, но не обработано          | Спан получения сообщения, кроме `order.submitted`                       | Спан смены статуса без ошибки в получившей системе             | 15 минут         | Д5, Д7    |
| Заказ получен в MES, но расчёт не начат       | Спан получения `order.submitted` в MES API                              | Спан «расчёт начат»                                            | 60 минут         | Д2, Д3    |
| Расчёт цены не завершился                     | Спан начала расчёта в MES API                                           | Спан расчёта с результатом                                     | 45 минут         | Д3        |
| Заказ API-клиента не создан в CRM             | Успешный расчёт по запросу API-клиента                                  | Смена статуса на `PRICE_CALCULATED` в CRM API с тем же заказом | 15 минут         | Д6        |
| Сообщение транспортной компании не обработано | Спан получения сообщения в CRM API                                      | Смена статуса на `CLOSED`                                      | 15 минут         | Условие   |

Сроки выведены из условия и порогов Task2:

- **60 минут** (сообщение к MES не получено, расчёт не начат): два самых долгих расчёта. MES может быть занят расчётами, и сообщение ждёт своей очереди.
- **45 минут** (расчёт не завершился): самый долгий расчёт из условия (30 минут) с запасом в половину. Срок отсчитывается от спана «расчёт начат», поэтому ожидание в очереди в него не входит, оно покрыто проверками на 60 минут.
- **15 минут** (сообщения к CRM, остальные сообщения к MES): совпадает с критичным порогом возраста сообщения в Task2. Для `order.submitted` эта проверка не применяется, за ним идёт расчёт, который проверяется отдельно.

После первых недель уточняем сроки по фактическим длительностям из метрик спанов, например берём 99-й процентиль длительности расчёта с запасом.

Для расчёта цены MES API в начале расчёта создаёт короткий спан «расчёт начат». Спан всего расчёта попадает в хранилище только по завершении, и без отметки начала зависший расчёт не увидеть.

Как работает:

- Найденные нарушения сторож записывает в отдельный индекс Elasticsearch: номер заказа, тип проверки, система, время, ссылка на поиск в Jaeger по `order.id`. Нарушение закрывается автоматически, когда ожидаемый шаг появился, или вручную после разбора.
- Наружу сторож отдаёт метрику «число открытых нарушений» с ярлыками `check` и `order.source`. Её забирает Prometheus, по ней срабатывают алерты.
- Проверяет только заказы, по которым шаг начался в последние 7 дней. Более старые зависания видны по метрикам возраста статуса из Task2.
- Ожидание людей (подтверждение продавцом, работа оператора) сторож не проверяет: сколько заказ может ждать человека, определяет бизнес, и это уже видно по возрасту статуса в Task2.

#### Алерты

Правила добавляем в тот же Prometheus и Alertmanager, что в [Task2](../Task2/Task2.md). Уровни, каналы и порядок реакции те же: предупреждение — сообщение в канал команды и тикет, критично — дежурному с повтором и эскалацией.

| Алерт                                        | Условие                                                                     | Уровень        | Что делаем                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------- | --------------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сообщение не получено                        | Открытых нарушений проверок «не получено» больше нуля                       | Критично       | Дежурный проверяет очередь и потребителя по runbook. Если сообщения в очереди нет, оно потеряно: дежурный передаёт заказ разработчику сервиса-публикатора (CRM API — Java, MES API — C#). Разработчик проверяет, не обработал ли получатель сообщение, и отправляет его заново. Без идемпотентности (Д5) повтор может задвоить обработку, поэтому автоматически и силами поддержки не переотправляем |
| Изменение статуса не дошло до другой системы | Открытых нарушений «получено, но не обработано» больше нуля                 | Критично       | По ссылке открыть трейс, найти ошибку, перейти в логи по trace id                                                                                                                                                                                                                                                                                                                                    |
| Заказ API-клиента не создан в CRM            | Открытых нарушений этой проверки больше нуля                                | Критично       | Создать заказ, предупредить продакт-менеджера: клиент ждёт                                                                                                                                                                                                                                                                                                                                           |
| Расчёт цены завис                            | Открытых нарушений «расчёт не начат» или «расчёт не завершился» больше нуля | Предупреждение | Проверить загрузку MES API, при зависании перезапустить расчёт                                                                                                                                                                                                                                                                                                                                       |
| Рост ошибок на шаге                          | Доля ошибок на шаге выше 5% за 15 минут (стартовый порог)                   | Предупреждение | Найти по метрике шаг и сервис, по трейсам — примеры заказов                                                                                                                                                                                                                                                                                                                                          |
| Переходы по статусам остановились            | За час ни одного перехода, который обычно бывает, в рабочее время           | Предупреждение | Проверить, что сервисы шлют спаны и что опрос и очередь работают                                                                                                                                                                                                                                                                                                                                     |
| Трейсинг не получает данные                  | От сервиса нет спанов 10 минут, или Collector недоступен                    | Критично       | Восстановить Collector или инструментацию. Пока данных нет, проверки сторожа недостоверны                                                                                                                                                                                                                                                                                                            |

В тексте каждого алерта сторожа есть ссылка на дашборд со списком заказов и на поиск в Jaeger. Дежурный сразу видит номера заказов и открывает их историю.

#### Дашборд

В Grafana из Task2 добавляем дашборд «Поток заказа по трейсам»:

- переходы между статусами в час, отдельно для магазина и API;
- длительность шагов (медиана и 95-й процентиль), в первую очередь расчёт цены и передача заказа;
- доля ошибок по шагам;
- таблица открытых нарушений из индекса сторожа: заказ, проверка, с какого времени, ссылка в Jaeger.

Grafana читает метрики из Prometheus, а таблицу нарушений — из Elasticsearch.

#### Как не дублировать мониторинг из Task2

| Вопрос                                                   | Отвечает Task2 (метрики из баз и очередей)          | Отвечает мониторинг по трейсам                       |
| -------------------------------------------------------- | --------------------------------------------------- | ---------------------------------------------------- |
| Сколько заказов зависло и как давно                      | Возраст заказа в статусе, число заказов по статусам | Не дублируем                                         |
| Копится ли очередь                                       | Глубина очереди, возраст сообщения, dead-letter     | Не дублируем                                         |
| Работает ли опрос Shop DB                                | Пульс опроса                                        | Не дублируем                                         |
| Какой именно заказ и на каком переходе застрял           | Нет                                                 | Сторож: номер заказа, проверка, система              |
| Сообщение ушло из очереди, но не обработано или потеряно | Нет: очередь пустая, метрики в норме (Д5)           | Сторож: публикация есть, получения или обработки нет |
| На каком шаге растут ошибки и задержки                   | Только по сервису в целом (RED)                     | Метрики из спанов по шагам заказа                    |

Чтобы одна проблема не порождала лавину алертов, в Alertmanager настраиваем подавление. Пока горят «Компонент недоступен» или «Опрос Shop DB остановился» из Task2 либо «Трейсинг не получает данные», алерты сторожа по затронутым проверкам не отправляются: причина уже известна, а нарушения по заказам остаются в таблице на дашборде.

## Безопасность

Трейсы содержат номера заказов, имена API-клиентов, маршруты запросов и ошибки, то есть по ним видно, как устроена система и кто с ней работает. Поэтому трейсинг защищаем как внутреннюю систему с конфиденциальными данными: минимум данных в спанах, доступ только сотрудникам по ролям, закрытая сеть и журнал доступа.

### Что защищаем и от чего

| Риск                                           | Чем опасен                                                                                      |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Персональные данные или секреты попали в спаны | Утечка через интерфейс трейсинга или хранилище, нарушение требований к персональным данным      |
| Посторонний открыл Jaeger или Elasticsearch    | Jaeger сам не проверяет пользователей. Кто открыл адрес, тот видит все трейсы                   |
| Сотрудник видит больше, чем нужно для работы   | Лишний доступ к данным клиентов и к prod                                                        |
| Подделка или засорение данных трейсинга        | Кто-то отправляет в Collector ложные спаны: ложные алерты сторожа или скрытие реальной проблемы |
| Внешний клиент влияет на трейсинг              | Подмена trace id или навязанное сэмплирование через входящий `traceparent`                      |

### Минимизация данных

Лучшая защита — не собирать лишнего. Список того, чего в трейсинге быть не должно, приведён в разделе «Анализ системы». Обеспечиваем его в двух местах:

- **В приложениях.** Тела запросов, ответов и сообщений не записываем. Заголовки запросов не записываем, кроме тех, что переносят контекст трейса. SQL-запросы записываются без значений параметров (в Java-агенте это поведение по умолчанию, в MES API включаем явно). Свои атрибуты добавляем только из утверждённого списка.
- **В Collector.** Последний рубеж на случай ошибки в коде. Collector пропускает только атрибуты из разрешённого списка, остальные удаляет. Значения, похожие на почту, телефон или токен, заменяет маской. Правила одни для всех трёх приложений.

Проверку того, что в спанах нет персональных данных, добавляем в проверку релиза в release: QA смотрит трейсы тестовых заказов.

### Доступ сотрудников

У Jaeger нет своей аутентификации, поэтому перед ним ставим прокси с входом через корпоративную учётную запись (SSO). Grafana уже работает с учётными записями сотрудников по [Task2](../Task2/Task2.md). Войти может только сотрудник с действующей учётной записью и нужной ролью. При увольнении учётная запись блокируется, и доступ пропадает сразу.

| Роль                    | Кто                                            | Доступ                                                                           |
| ----------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------- |
| Поддержка               | Продакт-менеджер и те, кто разбирает обращения | Просмотр трейсов prod в Jaeger, дашборд «Поток заказа по трейсам» в Grafana      |
| Разработчик             | Java- и C#-разработчики, QA, тимлид            | Просмотр трейсов всех окружений, дашборды. Изменять настройки трейсинга не могут |
| Администратор трейсинга | DevOps-инженер                                 | Настройка Collector, Jaeger, Elasticsearch и сторожа, управление доступами       |

Менеджеры по продажам доступа к Jaeger не получают: ответ по заказу клиенту они получают от поддержки. Прямой доступ к Elasticsearch есть только у администратора. Остальные работают через Jaeger и Grafana.

Так как у Jaeger нет разграничения прав внутри, роли разделяем на уровне прокси: для каждого окружения свой адрес Jaeger, и прокси пускает на адрес prod только роли «Поддержка» и «Разработчик».

### Сеть и технические учётные записи

- Collector, Jaeger, Elasticsearch и сторож доступны только из внутренней сети. Приём спанов Collector разрешён только с инстансов Shop API, CRM API и MES API (правила сетевого доступа).
- Приложения передают спаны в Collector по TLS с токеном. У каждого окружения свой токен, поэтому спаны из dev не попадут в prod.
- Соединения Jaeger, сторожа и Grafana с Elasticsearch идут по TLS под отдельными техническими учётными записями с минимальными правами: Jaeger пишет и читает индексы трейсов, сторож читает трейсы и пишет индекс нарушений, Grafana только читает. Кластер Elasticsearch общий с логами ([Task4](../Task4/Task4.md)), поэтому учётные записи трейсинга к индексам логов доступа не имеют.
- Collector ограничивает объём принимаемых данных и потребление памяти, чтобы поток спанов, случайный или намеренный, не уронил трейсинг.
- Токены и пароли технических учётных записей хранятся в секретах окружения, а не в коде и не в конфигурации в репозитории.

### Журнал доступа и сроки хранения

- Прокси перед Jaeger записывает, кто, когда и что искал, в том числе по какому `order.id`. Журнал уходит в централизованные логи ([Task4](../Task4/Task4.md)), его может просмотреть администратор при разборе инцидента.
- Сроки хранения ограничены (раздел «Хранение»): трейсы заказов 180 дней, остальные 14. Данные не копятся бессрочно.

### Защита снаружи

- Внешнего доступа к трейсингу нет: Jaeger, Grafana, Collector и Elasticsearch не публикуются в интернет.
- Рекомендация для сотрудников, работающих не из офиса: подключаться к внутренней сети через VPN, а не открывать трейсинг наружу ради удалённого доступа.
- API-клиенты и покупатели доступа к трейсингу не получают. Для обращения в поддержку клиенту достаточно идентификатора запроса, который MES API уже возвращает (Д6). Trace id наружу не отдаём.
- Входящий `traceparent` от внешних систем не принимаем (раздел «Передача контекста»): трейс начинается на нашей стороне, и внешняя сторона не может подменить trace id или решение о сэмплировании.
